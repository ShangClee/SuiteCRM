  ---
  What We Built: Thin-Hook-Fat-Service

  Account save event
         │
         ▼
  ┌─────────────────────────┐
  │  AccountsJjwg_Maps      │  ← THIN: ~5 lines per method
  │  LogicHook.php          │    just routes events
  └──────────┬──────────────┘
             │ delegates to
             ▼
  ┌─────────────────────────┐
  │  AccountGeocodeService  │  ← FAT: all business logic
  │  .php                   │    checks, loops, compares, saves
  └──────────┬──────────────┘
             │ calls
             ▼
  ┌──────────────────────────────────────────────────────┐
  │  jjwg_Maps::updateGeocodeInfo()                      │
  │  ├─ HTTP curl → Google Maps API (lat/lng lookup)     │
  │  └─ sets bean properties (no DB write)               │
  │                                                      │
  │  ORM: get_linked_beans() → bean->save()              │
  │  (one save per related record — N+1 pattern)         │
  └──────────────────────────────────────────────────────┘

  The key insight before we go further:

  The service actually does TWO fundamentally different things:

  ┌─────────────────────────────────────────────────────────┐
  │  Operation A: GEOCODE LOOKUP                            │
  │  Account address → HTTP → Google Maps → lat/lng         │
  │  ❌ Cannot ever live in a database                       │
  └─────────────────────────────────────────────────────────┘

  ┌─────────────────────────────────────────────────────────┐
  │  Operation B: GEOCODE PROPAGATION                       │
  │  Account lat/lng → copy to Projects, Opps, Cases,       │
  │  Meetings (already-computed values, pure data sync)      │
  │  ✅ This is just data movement — pure SQL               │
  └─────────────────────────────────────────────────────────┘

  So the question "move to stored procedure" really applies to Operation B only.

  ---
  Three Paths for Operation B

  Path 1: MySQL Trigger

  -- Fires AFTER accounts_cstm is updated
  -- (Google Maps call already happened in before_save)
  AFTER UPDATE ON accounts_cstm
  FOR EACH ROW
  BEGIN
    IF NEW.jjwg_maps_address_c != OLD.jjwg_maps_address_c THEN
      -- Bulk update all related Opportunities in one shot
      UPDATE opportunities_cstm oc
        JOIN accounts_opportunities ao ON ao.opportunity_id = oc.id_c
      SET oc.jjwg_maps_lat_c    = NEW.jjwg_maps_lat_c,
          oc.jjwg_maps_lng_c    = NEW.jjwg_maps_lng_c,
          oc.jjwg_maps_address_c = NEW.jjwg_maps_address_c
      WHERE ao.account_id = NEW.id_c AND ao.deleted = 0;
      -- repeat for project_cstm, cases_cstm, meetings_cstm
    END IF;
  END

  Elegant because: the trigger fires exactly when the data changes, with zero
  PHP code needed for propagation.

  Risky because:
  - SuiteCRM supports MySQL, PostgreSQL, Oracle, MSSQL — triggers are not
  portable
  - SuiteCRM ORM is unaware of triggers — its fetched_row cache won't reflect
  changes the trigger made; stale data risk
  - Invisible to the test suite — AccountGeocodeServiceTest wouldn't catch
  trigger failures
  - No existing triggers in the codebase — you'd be introducing a new pattern
  with no precedent

  Path 2: Stored Procedure (called from PHP)

  CREATE PROCEDURE sp_propagate_account_geocode(IN p_account_id CHAR(36))
  BEGIN
    DECLARE v_lat DECIMAL(10,6);
    DECLARE v_lng DECIMAL(10,6);
    -- fetch account geocode
    -- bulk update related tables
  END

  Called from the service:
  $this->db->query("CALL sp_propagate_account_geocode('{$accountId}')");

  Better than a trigger because: PHP still controls when it fires, visible in
  code review, testable by calling the procedure.

  Still risky because: same portability problem — this is MySQL-only in a
  multi-DB codebase.

  ---
  Path 3: Bulk SQL in the Service (Pragmatic Middle Ground)

  The service currently does this for Meetings already — direct SQL, no bean
  save:

  // Existing meetings pattern (already in jjwg_Maps.php):
  UPDATE meetings_cstm SET lat=?, lng=? WHERE id_c IN (
    SELECT id FROM meetings WHERE parent_id=? AND deleted=0
  )

  Extend the same pattern to Projects, Opportunities, Cases — replace the N+1
  ORM loop with a single bulk UPDATE JOIN per module:

  // Replace: foreach linked bean → bean->save()
  // With: one UPDATE JOIN query
  $sql = "
    UPDATE opportunities_cstm oc
      JOIN accounts_opportunities ao ON ao.opportunity_id = oc.id_c AND 
  ao.deleted = 0
    SET oc.jjwg_maps_lat_c     = ?,
        oc.jjwg_maps_lng_c     = ?,
        oc.jjwg_maps_address_c = ?
    WHERE ao.account_id = ?
  ";

  This is already the pattern the codebase uses for Meetings. It just wasn't
  applied consistently.

  ---
  The Deeper Question

  There's an interesting tension worth naming: why does an Account save need to 
  update related records at all?

  The current model is eager propagation — "Account saved? Immediately update
  all Projects, Opportunities, Cases, Meetings." This is:
  - Synchronous (adds to save time)
  - Fragile if related record count is large
  - Duplicates data across tables

  An alternative mental model: lazy lookup — store geocode on Account only, and
  have the map rendering JOIN to Account's geocode when displaying a related
  record. No propagation needed at all.

  This would mean: no sync logic anywhere, the fat service disappears, the hooks
   disappear. Just one geocoded entity (Account), and related records inherit it
   at query time.

  ---
  A few threads worth pulling on before deciding anything:

  1. Why does each related module need its own lat/lng copy? Is it because they
  can have their own address (independent of Account)? Or purely for map display
   convenience?
  2. How many related records does a typical Account have? If the answer is
  "hundreds of Meetings," the N+1 ORM pattern is already a problem in
  production.
  3. Is PostgreSQL support a real constraint for your deployment? If you're
  MySQL-only, stored procedures become more viable.

  What's the most interesting thread to you — the stored procedure/trigger path,
   the bulk SQL optimization, or the lazy-lookup architectural rethink?
